# Граница доступа агента

Агент сайта редактирует презентации через зарегистрированные MCP-инструменты редактора. Ему доступны HTML слайдов, CSS и оформление, заметки, аннотации и связанные ресурсы в пределах этих инструментов. Модель не получает инструмент выполнения серверных команд, прямой записи файлов, браузерного управления или подключения дополнительных интеграций. Запросы дополнительных разрешений автоматически отклоняются; интерфейса для их подтверждения нет.

## Разрешённый путь

OpenAI-совместимый режим получает функции из общего реестра `backend/modules/mcp/tools.js`. ACP подключает к Codex тот же реестр через `backend/modules/mcp/server.js` с контекстом текущей презентации и отдельным токеном. Изменения проходят через обычные операции хранения и проверку версии. Прямой доступ к каталогам сервера не нужен для изменения HTML или CSS: агент читает содержимое и передаёт исправленную версию инструменту редактора.

Импортированные слайды, шаблоны, заметки, комментарии и вывод модели считаются данными. Текст вроде «выполни команду» внутри презентации не расширяет доступ. Skills редактора читаются через `list_skills` / `read_skill`.

## Ограничения Codex через ACP

`backend/modules/ai/acp.js` запускает установленный адаптер с фиксированной конфигурацией:

- `INITIAL_AGENT_MODE=read-only`, `sandbox_mode=read-only`, `approval_policy=never`.
- Отключены `shell_tool`, `unified_exec`, shell snapshots, code-mode execution, просмотр локальных изображений, browser/computer use, генерация изображений и артефактов.
- Отключены apps, plugins, hooks, memories, host skill discovery и дополнительные агенты. Web search выключен.
- Автозагрузка проектных инструкций ограничена `project_doc_max_bytes=0`; команда уведомления пуста.
- Клиент не объявляет ACP-возможности прямого чтения/записи файлов или терминала.

Рабочая папка находится в `PROJECTS_DATA_DIR/ai/workspaces/<projectId>/`. Перед её созданием проверяются ID и наличие презентации. Файлы презентации не используются как `cwd`, поэтому импортированный `.codex/config.toml` или `AGENTS.md` не становится конфигурацией агента.

Процесс получает отдельные `HOME=<workspace>/.host` и `CODEX_HOME=<workspace>/.codex`. Сервер копирует туда только `auth.json` из операторского `CODEX_HOME` (либо `HOME/.codex`) с правами `0600`. Содержимое авторизации не печатается и не включается в контекст модели. Пользовательские config, MCP-серверы, hooks, skills и memories из операторского каталога не копируются. Существующая приватная авторизация сохраняется между запусками, чтобы не перезаписать её обновлённые токены.

После повторной авторизации операторского аккаунта уже существующие приватные каталоги автоматически не перезаписываются. Их обновление относится к администрированию сервиса. Не помещайте эти каталоги, auth-файлы или резервные копии в Git.

## Решение о разрешении

Клиент связывает исходное ACP-событие `tool_call` с его `toolCallId`. Разовое разрешение получает только точное имя зарегистрированного инструмента `mcp.presentations.<name>`. Заголовок самого запроса разрешения или последующее изменение отображаемого названия не могут превратить файловую операцию в доверенный вызов.

Неизвестный инструмент, неподтверждённый ID, чужая сессия, неактивный запрос и любая нативная операция не получают разрешение. Выбирается `reject_once` / `reject_always`, а при отсутствии подходящего отказа возвращается `cancelled`. Не создаётся событие `permission`, очередь ожидания или кнопка «разрешить». Совместимый метод подтверждения также возвращает `403`.

## Что подтверждено и что нужно проверять

`test/ai.test.js` проверяет реальный обмен JSON-RPC с mock ACP-процессом: автоматический отказ нативной операции, отказ подменённому названию, сохранение имени доверенного MCP-вызова, отсутствие события подтверждения, отдельные каталоги и импорт только тестовой авторизации. Тесты MCP и API проверяют проход к центральному хранилищу и конфликты версий. Они не обращаются к реальному аккаунту Codex.

Проверенные настройки относятся к включённому `codex-acp` 2.1.1 и установленному Codex 0.159.1. В этом адаптере режим `ReadOnly` явно устанавливает `approvalPolicy=on-request` при отправке хода, даже если `CODEX_CONFIG` содержит `never`. Поэтому защита не зависит только от этого флага: нативные возможности отключены, sandbox остаётся read-only, а клиент автоматически отклоняет дополнительные разрешения. Встроенный `apply_patch` не отключается устаревшим feature-флагом; его файловые изменения блокируются этими ограничениями.

При обновлении Codex или адаптера нужна отдельная проверка живого агента: запросить запуск команды, чтение/запись вне презентации и обычную HTML-правку через MCP. Команда должна быть недоступна, сторонний файл не должен измениться, а разрешённая правка должна сохраниться. Зафиксируйте наблюдаемый результат отдельно от успешных mock-тестов.

Это ограничение возможностей модели и разрешений ACP в доверенном установленном адаптере. `read-only` сам по себе не запрещает чтение и выполнение всех команд; именно поэтому командные инструменты отключены отдельно. Оно не изолирует произвольную операторскую программу, подставленную вместо адаптера, и не отменяет полномочия системного пользователя сервиса. Команду ACP задаёт оператор, браузер её не выбирает.

Официальные источники: [Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference) описывает feature-флаги и загрузку проектных инструкций; [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security) объясняет различие sandbox и approvals и поведение режима read-only. Реальное слияние конфигурации дополнительно проверено по установленному `node_modules/@agentclientprotocol/codex-acp/dist/index.js`.
